# Лицензирование и платежи

**Решение принято 2026-08-11: Paddle.** Ниже — обоснование выбора MoR, затем контракт для Block 09 и открытый вопрос Classic vs Billing, который надо закрыть до старта блока.

## Почему merchant of record, а не Stripe

Если брать платежи напрямую, продавец — вы, и вы обязаны собирать НДС в ЕС, GST в Австралии и налог с продаж в части штатов США, каждый со своим порогом и отчётностью. Для оборота в тысячи долларов это несоразмерно.

Merchant of record юридически становится продавцом: собирает налоги, выставляет инвойсы, разбирается с чарджбэками, платит вам одной выплатой. При цене $9 разница между 5% и 3% комиссии — 18 центов с продажи. Не оптимизировать, брать MoR.

## Classic или Billing — закрыто

**Решение владельца 2026-08-13: Billing, офлайн-схема.** Block 09 реализован по ней: подпись Ed25519 проверяется локально, сетевого кода в лицензировании нет. Раздел ниже оставлен как обоснование.

У Paddle две платформы, и лицензирование в них устроено по-разному: у Paddle Classic генерация и проверка лицензионных ключей была встроенной функцией, у Paddle Billing (куда идут новые регистрации) её, насколько известно, нет — там подписки, entitlements и вебхуки. Проверить в своём аккаунте, а не поверить этому файлу: документация Paddle меняется чаще, чем этот репозиторий.

**Если Classic** — берём встроенные ключи, схема ниже «онлайн-активация».

**Если Billing** — идём офлайн-схемой, и это, скорее всего, лучше в любом случае:

```
покупка → вебхук Paddle transaction.completed
        → Cloudflare Worker (~20 строк): подписывает "email|order-id" ключом Ed25519
        → письмо покупателю с ключом
        → приложение проверяет подпись встроенным публичным ключом, локально
```

```swift
let pub = try! Curve25519.Signing.PublicKey(rawRepresentation: Data(base64Encoded: PUBKEY)!)
// key = base64(payload) + "." + base64(sig), payload = "email|order-id"
pub.isValidSignature(sig, for: payload)
```

Почему это привлекательнее онлайн-активации: у приложения вообще исчезает сетевой код лицензирования, вместе с ним — весь класс отказов «нет сети → потерял Pro», лимит активаций и эндпоинт деактивации. Ключ работает на всех машинах покупателя, что для этой аудитории правильно. `CryptoKit` в стандартной библиотеке, зависимостей ноль.

Цена: отозвать ключ при возврате нельзя. При объёме в десятки продаж это дешевле, чем поддерживать сервер активаций.

## Контракт для Block 09

**Онлайн-схема (Classic):**
1. Эндпоинт активации: ключ + идентификатор установки → `valid / invalid / activation limit reached`.
2. Эндпоинт деактивации — освободить одну из трёх активаций.
3. Страница оплаты по URL, открывается в браузере из пейволла.

**Офлайн-схема (Billing):**
1. Проверка подписи локально, сеть не нужна.
2. Страница оплаты по URL, открывается в браузере из пейволла.
3. Вебхук и Worker живут вне репозитория приложения; публичный ключ — в бинарнике, приватный — у владельца.

В обоих случаях ответы и ключи разбираются по зафиксированным фикстурам в тестах; сеть в тестах не дёргается.

## Правила, не зависящие от схемы

- **Оффлайн-запуск обязан работать.** В онлайн-схеме — кэш в Keychain, повторная проверка не чаще раза в N дней и никогда не блокирующая: нет сети → остаёмся Pro. В офлайн-схеме проблемы не существует. Приложение, которое отваливается в самолёте, получает возврат и одну звезду.
- **Никакой привязки к железу.** Аудитория — люди, которые любят странные железки и меняют машины. Ключ на email.
- **Пиратство не лечим.** Кто обходит защиту, тот бы не заплатил. Каждая строка антипиратского кода — это баг, который сломается у честного покупателя.

## Возвраты

У продукта узкая аппаратная совместимость, поэтому порядок обязан быть: **скачал бесплатно → приложение подтвердило, что датчик есть → купил.** Это и есть главная защита от возвратов, и она реализована как гейт совместимости в Block 10. Возврат без вопросов в течение 30 дней — дешевле любого спора.
